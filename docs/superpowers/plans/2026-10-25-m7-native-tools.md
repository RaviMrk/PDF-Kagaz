# Milestone 7 — v1.1 Native Tools Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Six new tools go live: Compress (T-06), Protect with password (T-07), Remove password (T-08), PDF to images (T-09), Add watermark (T-10), Add page numbers (T-11) and Sign PDF (T-12) with saved signatures. Any tool can open a password-protected input after the user types its password. Files over the pdf-lib caps (30 MiB per file, 100 MiB per merge) go to a Kotlin PdfBox implementation of the same operation instead of being refused, which closes the M4 carry for merge, split and organise. Long jobs keep running in the background under a `dataSync` foreground service that shows progress and can be cancelled from the notification. After the third successful tool use, the app asks for an in-app review (A-05). The milestone ends with a minified release build, a size gate, a manifest check and an emulator smoke test of every new tool.

**Architecture:** `modules/pdf-native` gains PdfBox-Android, which handles security (inspect, check password, decrypt, AES-256 encrypt), page assembly, compression and stamping. It also gains PdfRenderer page export, a native signature pad view and a foreground service. Every native op reads a file staged in the job workspace (`cacheDir/tools/<jobId>/`), writes its result to the same workspace, reports progress through an `onToolProgress` event and stops between pages when `cancelNativeTool(jobId)` is called. `runTool` becomes a dispatcher over per-tool runners in `src/services/tools/runners/`. These share a `RunContext` that does the staging, decrypts locked inputs with the password the user typed, chooses the route (pdf-lib or native) from the staged sizes, and publishes outputs. Watermark, page numbers and sign are all expressed as one `StampSpec`. The spec is applied by pdf-lib (`src/services/pdf/stamp.ts`) or by PdfBox (`PdfStamper.kt`), and both sides use the same geometry, pinned by one shared vector file. Passwords exist only in memory: in screen state and in the in-process `ToolRequest`.

**Tech Stack:** Expo SDK 57 (`expo@~57.0.30`, RN 0.86.3, New Architecture), Expo Router, Zustand 5, expo-sqlite + Drizzle, MMKV, `@cantoo/pdf-lib@^2.11.1` (its `encrypt()` defaults to AES-256 V5/R6, which is how `__fixtures__/protected.pdf` is made). **New:** `com.tom-roush:pdfbox-android:2.0.27.0` (latest on Maven Central, checked 2026-10-24; pure Java with no `.so`, so it has no 16 KB impact; AAR 3.25 MB; pulls `bcprov`/`bcpkix`/`bcutil-jdk15to18:1.72`), `org.robolectric:robolectric:4.17` (test only), `expo-store-review@~57.0.3` (the SDK 57 bundled version; Play In-App Review, no permissions). No WebView, Skia or SVG package is added.

**Spec:** `docs/REQUIREMENTS.md` §2 (v1.1 row), §3.3 T-06–T-12, §3.4 A-05, §4 (memory, background work, app size, accessibility, localisation, reliability), §5 (`POST_NOTIFICATIONS` only for long-running tool progress), §6 (PdfBox-Android, pdf-lib limit, signature), §7.2 `signatures`, §7.3 native API, §8 (`/signature`, `PasswordDialog`, `PagePicker`, `ProgressSheet`, Tools groups, Home quick tools), §9 item 7, §10.1–10.2. **Decisions this plan makes (the spec leaves them open):**
- **Locked inputs.** `inspectPdf` reports `PdfLock = 'none' | 'open' | 'password' | 'restricted'`. `'open'` means encrypted, but the empty password grants editing; it is decrypted silently. `'password'` means a user password is needed. `'restricted'` means it opens without a password but forbids changes, so the owner password is asked for. A decrypted working copy is made only when the opening password gives owner permission, or `canModify && canAssembleDocument && canExtractContent`. Otherwise the result is `ERR_PASSWORD_RESTRICTED`, so restrictions are never bypassed. Outputs made from a locked input carry no password (except Protect), and the result screen says so.
- **Protect:** AES-256 (`keyLength 256`), with the owner password the same as the open password, so Remove password works with it later. New password: 4 or more characters and at most 127 UTF-8 bytes; it must match the confirm field.
- **Compress** levels (Kotlin `CompressLevels`, JS passes the key): `low {maxLongSidePx 2400, jpegQuality 80, dropThumbnails false}`, `medium {1600, 65, true}`, `high {1024, 50, true}`. Eligible images are 8-bit DeviceGray/DeviceRGB/ICCBased (N = 1 or 3) with DCT or Flate, at least 64 px each side. An existing SMask is kept and reattached. JPX, JBIG2, CCITT, CMYK, Indexed, image masks and inline images are left alone. A stream is replaced only when the new one is under 90 % of the old. Unfiltered streams get Flate. Shared XObjects are processed once. PdfBox 2.0 cannot write object streams; the full rewrite on save drops unreferenced objects instead. When `after >= before`, the output is still published (never over the original), and the result warns and offers **Delete new file** ("keep the original") or **Keep both**.
- **PDF to images:** JPG (quality 90) or PNG, on white. `dpi ∈ {72, 150, 300}`. Pages are all pages or a PagePicker selection. Scale = `min(dpi / 72, sqrt(RENDER_MAX_PIXELS / (wPt × hPt)))`, and the result counts pages saved at a lower resolution. Files go to `Pictures/PDFToolkit/<name> pages/<name> p<NNN>.<ext>` (page number zero-padded to the page-count width). Locked inputs are decrypted to the workspace first, because PdfRenderer cannot open them.
- **Routing:** `merge`, `split`, `organize`, `watermark`, `page-numbers` and `sign` run in pdf-lib when the staged (decrypted) sizes fit `JS_CAPS`, otherwise in PdfBox within `NATIVE_CAPS`. `compress`, `protect`, `unlock` and `pdf-to-images` always run natively. Images to PDF and Scan are unchanged.
- **Stamping:** one `StampSpec` covers watermark, page numbers and signatures. A text watermark is rendered to a transparent PNG natively (any script, including Devanagari) and stamped as an image. Page numbers are real text in Helvetica (Standard 14). When the localised template is not WinAnsi-encodable, the fallback `{n} / {total}` is used; font embedding for mr/hi is v1.2 work. There is no live preview of watermark or page numbers in v1.1.
- **Signature pad:** a native Expo view in `pdf-native` (Android `Canvas` drawing, smoothed quadratic paths, export of a trimmed transparent PNG). It adds no dependency. PNGs are stored in `filesDir/signatures/` with rows in `signatures` (existing table, no migration). At most 10 saved signatures.
- **Background:** every job starts `ToolJobService` (`foregroundServiceType="dataSync"`; Play lists "local file processing" under dataSync) while the app is in the foreground, when the job starts. Android 12+ defers a foreground service notification for 10 s, so short jobs show nothing. The service uses `stopWithTask="true"`: swiping the app away kills the job, and the existing interrupted-job recovery reports it on the next start. **Cancel** in the notification cancels the job. A job that finishes while the app is not active posts one "finished/couldn't finish" notification that opens `/result?jobId=…`. `POST_NOTIFICATIONS` is requested once, at the first job on Android 13+; denial changes nothing else.
- **Review (A-05):** after the 3rd successful job, ask once per install, on **Done** of a successful result, before leaving the result screen. That keeps the prompt off the reader; Open, Share and failed jobs never ask.

Tests: Task 8 `stampGeometry.test` and `StampGeometryTest` over the same `__fixtures__/stamp-vectors.json`; `stamp.test` on `mixed-sizes.pdf` page 3; Task 11 device check on a rotated page.

5. **Compress on a PDF it cannot shrink** (text-only, already optimised, JBIG2 scans, an image with an SMask). ## Planner rulings

- Native ops write to the job workspace and return `WorkspaceFile`, rather than the spec's `compress(uri) → {outUri, before, after}` shapes, so staging, publishing, cancel and cleanup stay uniform with M4/M5.
- PdfBox-Android 2.0.27.0 is the latest stable; it is pure Java, so it has no 16 KB impact. `bcpkix`/`bcutil` are excluded because only the symmetric AES path is used (proven by the Task 1 round-trip test). There is a size gate at Task 1 (stop at ≥ 34 MB arm64 download) and the hard < 40 MB gate at Task 14.
- Robolectric 4.17 (test only) runs the PdfBox JVM tests with the real fixtures, because PdfBox-Android needs Android resources and Bitmap.
- All three pdf-lib tools (watermark, page numbers, sign) get a native twin through one shared `stampPdf` op. A large scanned contract is exactly the file people sign or number, and one op serves all three, so blocking them at the cap was not chosen.
- The M4 "native in M7" carry is honoured: merge, split and organise over the JS caps run through one `assemblePdf` op.
- Native caps are 512 MiB per file and 1 GiB per job. PdfBox uses mixed memory (16 MiB heap, then temp files in the workspace).
- A text watermark is rendered to PNG natively, so any script works without font embedding. Page numbers use Helvetica with a `{n} / {total}` fallback; font embedding is v1.2 with mr/hi.
- Geometry is implemented twice (TS and Kotlin), and both are pinned by one shared `stamp-vectors.json`, so the two routes cannot drift.
- Signature pad: a native Expo view instead of react-native-signature-canvas (needs WebView, ~1 MB, slow first paint, base64 bridge), Skia (~6 MB/ABI) or SVG + gesture-handler (touch points through JS). It adds no dependency, draws natively and works with the New Architecture.
- Saved signatures: at most 10; PNGs in private `filesDir/signatures/`; the existing `signatures` table is used with no migration (dimensions come from the PNG).
- Locked inputs: there are four lock states; owner-restricted PDFs require the owner password, so restrictions are never bypassed. Outputs from locked inputs carry no password, and the result says so.
- Protect uses AES-256 with the owner password the same as the open password, so the app's own Remove password works; the new password is 4 characters to 127 bytes.
- Passwords exist only in component state and the in-memory request (kept for an in-process retry until dismiss). A DB retry of protect/unlock returns `needsInput`; other tools retried from the DB fail `encrypted` with "start again" copy.
- The watermark text is stored in `tool_jobs.options` (local DB, backups off, never in telemetry) so a retry works. This differs from M5's untyped-name rule, because a watermark is content, not identity.
- Compress publishes even when the output is larger, then offers "Delete new file" (keep the original) or "Keep both". Holding the temp file across the result screen would break the workspace-cleanup invariant.
- Compress has no object streams (PdfBox 2.0 cannot write them). The full rewrite on save, Flate for unfiltered streams and dropping thumbnails at medium/high stand in for them.
- PDF to images writes to `Pictures/PDFToolkit/<name> pages/` through MediaStore without `READ_MEDIA_*`, using legacy storage access on API 24–28. The pixel clamp is 12 MiP per page (A4/Letter/Legal at 300 DPI fit), and clamped pages are reported.
- PDF to images publishes page by page from a JS loop over `renderPdfPage`/`publishImageOutput` (renderer kept open natively), so cancel keeps the pages already saved, like split.
- Foreground service type is `dataSync`: Play lists local file processing under it. `shortService` was rejected because of its 3-minute limit; `mediaProcessing` (API 35+ only) because it is not meant for documents. Play requires the Console declaration as a user action.
- The service starts at every job start: Android 12+ defers foreground service notifications for 10 s, so short jobs stay silent, and starting later from the background is forbidden. `stopWithTask="true"` makes swipe-away an explicit kill handled by the existing interrupted-job recovery.
- `POST_NOTIFICATIONS` is requested once at the first job on Android 13+ through RN `PermissionsAndroid` (no expo-notifications, which would pull in FCM); denial is silent. A "finished" notification is posted only when the app is not active.
- The review prompt (expo-store-review ~57.0.3) asks once per install after 3 successes, on Done of a success, before leaving the result screen, so it never shows over the reader. The interstitial call next to it is untouched.
- Ads: there are no ad tasks and no ad checks, and the ads SDK's manifest entries are accepted as they are, per the controller (a separate change turns ads off behind a flag).
- There is no live preview of watermark or page numbers in v1.1; the result's Open shows the output.
- The §2 v1.1 item "recent/favourites sync polish" is not in M7. It names no requirement ID or acceptance criterion and is not in §9 item 7; it is left to the user to define. Cost if wrong: one small follow-up task.
