# Milestone 5 — Images to PDF and Document Scanner Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Images to PDF (T-04: pick photos from the system Photo Picker, reorder, page size A4 / Letter / fit, margins, orientation) and Camera scan to PDF (T-05: Google ML Kit Document Scanner for capture, automatic edge detection, crop and its own filters, plus our Colour / Greyscale / Black & white filter, multi-page, reorder, name) work end to end. Both run through the M4 tool job runner, store, progress sheet and result screen, so cancel, background, interrupted-job recovery and Open / Share / Save as come with them. They need no CAMERA or media permission.

**Architecture:** Bitmap work happens in Kotlin and the PDF is assembled in JS. Picked images and scanner pages are copied at once into a private **image session** workspace `cacheDir/tools/img-<id>/src-<n>`. Picker and scanner grants are short-lived, and JS never sees their URIs. When a job runs, `pdf-native.prepareImagePage` decodes each source with `inSampleSize`, scales it to at most 2400 px on the long side, applies EXIF orientation and the filter, draws it onto white (so transparency never turns black), re-encodes it as JPEG q85 into the job workspace, and returns its size. `src/services/pdf/imagesToPdf.ts` (`@cantoo/pdf-lib`, Jest-tested on fixture JPEGs) embeds those JPEGs one at a time without decoding them, using page boxes from `src/services/pdf/imageLayout.ts`. The output is published with the existing `publishToolOutput` (temp file, then a never-overwrite publish) and indexed as an `output` row. `src/services/tools/imageSession.ts` is the only thing screens call to pick images, scan, show thumbnails and discard a session.

**Tech Stack:** Expo SDK 57 (`expo@~57.0.30`, RN 0.86.3, New Architecture), Expo Router (typed routes), `@cantoo/pdf-lib@2.11.1`, `expo-file-system@~57.0.7` (via `toolFs.ts`), `react-native-sortables@1.10.1`, `@shopify/flash-list@2.0.2`, Zustand 5, expo-sqlite + drizzle; Kotlin Expo module `pdf-native` + **new** `com.google.android.gms:play-services-mlkit-document-scanner:16.0.0`, `androidx.exifinterface:exifinterface:1.4.2`, `androidx.activity` (`ActivityResultContracts.PickMultipleVisualMedia`, already on the classpath through expo-modules-core / ML Kit); Jest (jest-expo, `expo-router/testing-library`), JUnit 4.13.2.

**Spec:** `docs/REQUIREMENTS.md` (sections 1 core principles; 3.3 common flow + T-04, T-05; 3.4 A-01 "scan quality" (M6 setting, fixed constants here); 4; 5 (CAMERA row: not needed); 6 (pdf-lib for images to PDF, ML Kit scanner wrapped in pdf-native, size limit); 7.1 (`src/services/pdf/imagesToPdf.ts`), 7.3 `scanDocument`; 8 `/scan` route; 10.1–10.2 (16 KB); 11 ML Kit row). **Decisions this plan makes (the spec leaves them open). Checked against node_modules, dl.google.com Maven and the ML Kit / Expo v57 docs on 2026-10-23:**
- **Photo picker = our own `PickMultipleVisualMedia(ImageOnly)` inside pdf-native, not `expo-image-picker`.** The expo-image-picker v57 docs say its library manifest adds `CAMERA`, `READ_EXTERNAL_STORAGE` and `WRITE_EXTERNAL_STORAGE`, and its plugin adds `RECORD_AUDIO` by default. It also copies picks into its own cache, outside our guarded workspace. The androidx contract uses `ACTION_PICK_IMAGES` where it is available (API 33+, or API 30+ with SDK extension 2) and falls back to `ACTION_OPEN_DOCUMENT` `image/*` otherwise. It needs no permission. We wrap it in an Expo `AppContextActivityResultContract` (it delegates `createIntent`/`parseResult`), so a result survives activity recreation the way M4's pickers do. The GMS photo-picker backport for API < 30 (a manifest `ModuleDependencies` service) is not added; DocumentsUI is the fallback there.
- **Images reach the PDF in two stages.** First, native preparation bounds memory: one bitmap at a time, `inSampleSize` decode and then an exact scale to ≤ 2400 px, so the worst case is a decode under 4800 px on the long side, about 69 MB in ARGB, released before the next image. Second, pdf-lib embeds the JPEGs in JS without decoding them (`embedJpg` only parses the header), keeping the spec 6/7.1 choice of "images to PDF with pdf-lib" and Jest coverage on fixtures. Android `PdfDocument` was rejected because it re-encodes bitmaps losslessly, which makes outputs many times larger. A hand-written native PDF writer was rejected because the existing JS pipeline already covers publish, cancel, progress and tests. HEIC/HEIF decodes on API 28+ only. Older phones get `ERR_IMAGE_INVALID` at import ("couldn't be added").
- **EXIF orientation** is read with `androidx.exifinterface` 1.4.2 from the session copy. All 8 orientations are applied with one `Matrix` (pure `ExifTransform`) while drawing onto a white `ARGB_8888` canvas, so PNG/WebP transparency comes out white. Prepared JPEGs carry no EXIF.
- **Page layout** (pure TS, `imageLayout.ts`, PDF points, origin bottom-left): A4 = 595 × 842, Letter = 612 × 792. Margins: none 0, small 18 (¼ in), large 36 (½ in). Orientation `auto` makes a page landscape when the image is wider than tall; `portrait`/`landscape` force it. The image is scaled to fit the box inside the margins (up or down, aspect kept) and centred. **Fit** = the image scaled so its long side is 842 pt (A4's long side, independent of camera resolution), with the page equal to that box plus the margins on every side. Orientation is ignored for fit (the UI disables it). Defaults: Images to PDF `a4` / `auto` / `small`; Scan `fit` / `auto` / `none`.
- **Scanner = ML Kit `GmsDocumentScanning` 16.0.0**, `SCANNER_MODE_FULL`, `RESULT_FORMAT_JPEG` only, `setGalleryImportAllowed(false)`, `setPageLimit(remaining capacity)`. The AAR (checked) has no `.so` and no permissions, declares minSdk 23, and adds only an invisible delegate activity. It is launched through Expo's activity-result registry with an `ACTION_INTENT_SENDER_REQUEST` intent carrying the `IntentSender` from `getStartScanIntent(activity)`. Expo's `AppContextActivityResultRegistry` supports that path. **From ML Kit's UI:** capture, automatic edge detection, crop, rotate, page reordering inside the scanner, its filters (auto-enhance / colour / greyscale; ML Kit documents no black-and-white filter) and stain/finger cleaning. **From our review screen:** a document-level filter Colour (as scanned) / Greyscale / Black & white (applied natively when preparing pages, previewed with native thumbnails), reorder, delete, "Scan more pages", page size, margins and name. We use the scanner's page JPEGs rather than its PDF result, so scans share the images pipeline, its options and our filters. This deviates from spec 7.3's `scanDocument(): Promise<string /* PDF uri */>`: ours returns imported page descriptors.
- **Play services unavailable:** `scanDocument` pre-checks `GoogleApiAvailability.isGooglePlayServicesAvailable == SUCCESS`, then maps any `getStartScanIntent` failure to `ERR_SCANNER_UNAVAILABLE`. `/scan` shows copy saying the scanner needs Google Play services (and one connection the first time), with a button to open Images to PDF. A scanner cancel is not an error.
- **Jobs:** `ToolRequest` gains `{ toolId: 'images-to-pdf' | 'scan'; inputIds: []; sessionId; images; filter; layout; name }`. The runner, store, `ProgressSheet`, `/result` and `ActiveJobCard` are reused. The session is deleted by the store after a successful job. On failure or cancel it is kept for "Try again" in this process. A process death loses it, because `cleanupToolLeftovers(APP_STARTED_AT)` deletes old sessions at the next start. Retry then answers `gone` with "add them again" copy. The flow screen deletes its session when the user leaves without starting a job.
- **Output names:** `"Images 2026-10-23 14.05.pdf"` / `"Scan 2026-10-23 14.05.pdf"` (local time, `.` instead of `:`), or the user's name from the name field, cleaned with `outputBaseName` (M4).

## Review Focus

1. **Many or huge photos** (100 × 12 MP photos, a 50 MB PNG, a 20000 × 1500 panorama, 101 picks through the DocumentsUI fallback) should be refused or bounded with a clear notice and never crash with OOM. Imports are capped at 100 and the notice says so; each page is prepared at ≤ 2400 px; a panorama keeps its aspect ratio. Tests: Task 2 `ImageSizingTest` (panorama, tiny image never upscaled), Task 4 `imageSession` (limit notice, picks sliced), Task 4 `runTool` (`totalTooLarge` from prepared sizes), Task 8 (30 photos, PSS recorded).
2. **Odd images** (EXIF-rotated JPEG, PNG with transparency, a `.jpg` that is not an image, HEIC on API < 28, a 1 × 1 px image) should come out upright and on white, and an unsupported file is not added, with a "couldn't be added" count. Nothing should be a black or sideways page. Tests: Task 2 `ExifTransformTest` (all 8 orientations), `ImageFiltersTest`, Task 4 (`ERR_IMAGE_INVALID` counted, not thrown), Task 8 (device: `exif-rotate-90.jpg`, `alpha.png`, `not-an-image.jpg`).
3. **Scanner unavailable or interrupted** (no or outdated Play services, offline first run, low-RAM `UNSUPPORTED`, the user backs out of the scanner, "Scan more" cancelled) should give the unavailable copy plus an Images to PDF button for errors. A cancel with no pages leaves the screen; a cancel during "Scan more" keeps the existing pages. Tests: Task 3 (`ScanResults`, error mapping), Task 7 (`scan.test.tsx` cases), Task 8 (launch on both emulators; failure path or listed as a user action).
4. **Process death and retry** (app killed mid-job, killed while the picker or scanner is open, "Try again" after a restart) should leave no partial output and no session leftovers. The interrupted job shows on Home; retry says the images are gone; photos are untouched. Tests: Task 4 (store `retry` → `gone`, session cleaned only on success, runner `imagesGone`), Task 8 (`am force-stop`, `ls -a`, sha256 of the pushed photos).
5. **User-typed names** (`""`, `"   "`, `"../x"`, `"a/b:c?.pdf"`, 120 Devanagari characters, a name that already exists in `Documents/PDFToolkit`) should become a valid, cleaned, never-overwriting name, with the default used when the field is empty. Tests: Task 1 `outputNames` (`customOutputName`), Task 4 (`runTool` publishes the cleaned name), Task 8 (same name twice → `(2)`).
