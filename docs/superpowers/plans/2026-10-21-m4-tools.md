# Milestone 4 — Tool Framework, Merge, Split and Organise Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Merge (T-01), Split (T-02) and Organise pages (T-03) work end to end through one generic tool flow (pick → options → progress → result with Open / Share / Save as), write only new files into `Documents/PDFToolkit/` (temp file, then move; never overwriting anything), are indexed as `output` rows, keep running when the user leaves the tool screen, and are reachable from the Tools tab (all T-01–T-14, grouped, unimplemented ones "coming soon"), the Home quick tools and a new long-press multi-select in Files. Four Milestone 3 review residuals are fixed first.

**Architecture:** Screens never see bytes. `src/services/pdf/{loadPdf,merge,split,organize}.ts` are pure `@cantoo/pdf-lib` functions over `Uint8Array`s (Jest-tested against the real fixtures in the node environment). `src/services/tools/runTool.ts` orchestrates a job: size checks → `pdf-native` stages each input into a private workspace `cacheDir/tools/<jobId>/` with a guarded stream copy (UriGuard, open-then-verify, size cap) → bytes are read with `expo-file-system` → the pdf service runs → output bytes are written to the workspace → `pdf-native.publishToolOutput` copies them to `Documents/PDFToolkit/.<name>.part` and renames (all-files access / legacy storage) or inserts a pending MediaStore item and publishes it (SAF mode) → `filesStore.registerOutputs` indexes them as `output` under the writer lock. A Zustand `toolJobStore` owns the one running job (progress, cancel, retry) and the `tool_jobs` row, so navigation never cancels work. Organiser and split page grids use their own native thumbnail lane (`ToolThumbnails`, own mutex and renderer) on a staged preview copy, never the reader's lane or cache.

**Tech Stack:** Expo SDK 57 (`expo@~57.0.30`, RN 0.86.3, New Architecture), Expo Router 57 (typed routes), `@cantoo/pdf-lib@2.11.1`, `expo-file-system@~57.0.7` (new `File` API: async `bytes()`, `write(Uint8Array)`), `react-native-sortables@1.10.1` (+ existing `react-native-reanimated@4.5.1`, `react-native-worklets@0.10.1`, `react-native-gesture-handler@~2.32.0`), Zustand 5, expo-sqlite + drizzle-orm 0.45 (drizzle-kit 0.31), `@shopify/flash-list@2.0.2`, Kotlin Expo module `pdf-native` (`PdfRenderer`, `MediaStore`, `ACTION_CREATE_DOCUMENT`/`ACTION_OPEN_DOCUMENT`), Jest (jest-expo, `expo-router/testing-library`, better-sqlite3), JUnit 4.13.2.

**Spec:** `docs/REQUIREMENTS.md` (sections 1 core principles, 3.3 T-01–T-03 + common flow, 4, 5 POST_NOTIFICATIONS row, 6 pdf-lib limit, 7, 8 routes and shared components, 9 milestone 4, 10.1)

- Native error codes: exactly `ERR_FILE_NOT_FOUND`, `ERR_PDF_ENCRYPTED`, `ERR_PDF_INVALID`, `ERR_PERMISSION_DENIED`, `ERR_FILE_EXISTS`, `ERR_INVALID_NAME`, `ERR_PASSWORD_UNSUPPORTED`, `ERR_NO_ACTIVITY`, `ERR_IO`, `ERR_VOLUME_UNAVAILABLE`, plus **one new code in M4: `ERR_TOO_LARGE`** (Task 4; added to `PDF_NATIVE_ERROR_CODES`). Error messages never contain names, paths or URIs.
- Row removal rule: only a confirmed `ERR_FILE_NOT_FOUND` may remove an index row (`useFiles.dropMissing`). `ERR_VOLUME_UNAVAILABLE`, `ERR_IO`, `ERR_PERMISSION_DENIED`, `ERR_TOO_LARGE` and anything else show a message and keep the row.
- Never overwrite or modify an original or any existing file. Every write goes to a temp file first (`cacheDir/tools/<jobId>/out-<n>.pdf`, then `Documents/PDFToolkit/.<name>.part` or a pending MediaStore item) and is renamed/published only when complete; a name that exists gets `" (2)"`, `" (3)"`… (`FileNames.uniqueName`). There is no "Replace original" in M4.
- Share / URI security surface stays as in M3: the FileProvider exposes `cacheDir/reader` and `cacheDir/share` only; every read on behalf of the user of a `file://` goes through `UriGuard` (`requireAllowed` + `openVerified`, open-then-verify) and every `content://` through `requireAllowed` (own providers refused). The tool workspace `cacheDir/tools` and `cacheDir/tool-thumbs` are never added to `PathRules.cacheDirs` and never shared; results are shared from their published location.
- JS size limits (spec 6): one input ≤ `JS_MAX_FILE_BYTES = 30 * 1024 * 1024`; a job's inputs together ≤ `JS_MAX_TOTAL_BYTES = 100 * 1024 * 1024`. Bigger inputs are refused before any byte reaches JS (row size check, then the native stage cap for providers that report no size).
- Index writes that can race a scan (`registerOutputs`) go through the files-store writer lock (`exclusive`).
- Privacy: no file names, paths or URIs in logs, error messages, `tool_jobs.options` or `tool_jobs.error` (options hold only modes, page numbers and range text; error holds a failure code). Allowed log (release too): `` `[tool] ${toolId} ${ms}ms ${pages} pages ${outputs} files` `` — Task 13 measures with it.

**Decisions this plan makes (spec leaves them open), checked against node_modules / Maven Central / package sources on 2026-10-21:**
- **Large files: refuse in M4, route natively in M7 (no PdfBox yet).** Checked `com.tom-roush:pdfbox-android` on Maven Central: latest 2.0.27.0, AAR 3.25 MB (6.4 MB unpacked: 1.76 MB `classes.jar` + fontbox/cmap assets), no `.so` (pure Java, so no 16 KB issue), but it pulls `bcprov`/`bcpkix`/`bcutil-jdk15to18:1.72` (BouncyCastle, several MB) and needs `PDFBoxResourceLoader.init(context)`, so its tests are instrumented, not JVM. With R8 not enabled until M6, adding it now costs APK budget (spec 4: < 40 MB) for a path M4 does not need; M7 adds it anyway for compress/encrypt and will add `mergeNative`/`splitNative` (`PDFMergerUtility` + `MemoryUsageSetting.setupTempFileOnly()`) behind the same `runTool` entry. M4 refuses with a clear message: a file over 30 MB → `tooLarge`, inputs over 100 MB together → `totalTooLarge`. The 50 MB fixture is therefore refused gracefully (Task 13 checks the message and that nothing is written).
- **pdf-lib behaviour (verified in node against the fixtures):** `PDFDocument.load` of `protected.pdf` throws `EncryptedPDFError`; owner-password-only PDFs also throw it and would load with `{ password: '' }`, which would silently strip their protection — **M4 refuses every encrypted input** (`encrypted`; unlock is T-08 in M7). `corrupted.pdf` *loads* with default options (1 page, garbage on save) but throws with `{ throwOnInvalidObject: true }`; all other fixtures load strictly → inputs are loaded with `{ throwOnInvalidObject: true, updateMetadata: false }`. `copyPages` keeps MediaBox and `/Rotate` (merge of mixed-sizes gives `[595×842 0°, 792×612 0°, 595×842 90°]`); copying the same index twice yields two distinct page refs (duplicate works); outlines, AcroForms and links are not carried into outputs (documented limitation). Timings (node, M-series): load 50 MB 21 ms, 1,000-page merge+save 145 ms.
- **Bytes into/out of JS through `expo-file-system@57.0.7`** (already resolved transitively by `expo`; Task 7 makes it a direct dependency): `File.bytes()` is an `AsyncFunction` returning `Uint8Array`, `File.write(Uint8Array)` writes typed arrays. Inputs are **always** staged by `pdf-native` (also `file://` ones), so JS only ever reads the private workspace and every read of a user file passes UriGuard's open-then-verify.
- **Drag library = `react-native-sortables@1.10.1` (pinned exactly), not `react-native-draggable-flatlist`.** Checked: sortables 1.10.1 (2026-09-26) changelog "Support react-native-reanimated 4.5 / worklets 0.10", peers `reanimated >=3`, `gesture-handler >=2`, provides `Sortable.Grid` with `columns`, `keyExtractor`, `onDragEnd({ data, fromIndex, toIndex })`. `react-native-draggable-flatlist@4.0.3` was last published 2025-05, has no grid (`numColumns` unsupported) and makes no Reanimated 4 claim. Sortables is not virtualised, so the organiser accepts PDFs of up to `ORGANIZE_MAX_PAGES = 300` pages ("Split the PDF first" beyond). Device gate in Task 9.
- **Background work in M4:** jobs run in JS inside `toolJobStore` (not a screen), so leaving the tool screen ("Continue in background") or the app (process alive) keeps them running; Home shows an `ActiveJobCard` with progress and, when done, "View". No notification, foreground service or `POST_NOTIFICATIONS` in M4: under the size caps a job takes seconds (spec target < 10 s); M7's native long tools (compress, OCR, > 100 MB merges) add WorkManager + a progress notification + the API 33 permission request. If the process dies mid-job, the next start marks the job `failed`/`interrupted` and deletes leftovers; nothing partial is ever visible.
- **Split modes:** "Page ranges" → one file per comma-separated item (`"1-3, 5, 8-10"` → 3 files); "Every N pages" → `ceil(count / N)` files; "Extract pages" → one file with the selected pages in ascending order (PagePicker: range text ⇄ thumbnail grid).
- **Output names** (localised via `output.*`, base = sanitised input name without `.pdf`, R4): merge `"<first> merged.pdf"`, split ranges `"<name> pages 1-3.pdf"` / `"<name> page 5.pdf"`, every N `"<name> part 2.pdf"`, extract `"<name> extracted.pdf"`, organise `"<name> organised.pdf"`; uniqueness `" (2)"` is decided natively at publish under a lock. In SAF/MediaStore mode the provider uniquifies (it cannot see other apps' files).
- **Save as** = `ACTION_CREATE_DOCUMENT` (user picks folder and name) and a guarded copy of the published output; **Browse files** in the picker = `ACTION_OPEN_DOCUMENT` (multiple, `application/pdf`), registered like incoming files (`source 'intent'`, `folder ''`), so tools work in permission mode `'none'` too.
- **`tool_jobs`** gains `output_ids` (JSON `string[]`, default `'[]'`) via migration 0003; `output_uri` keeps the first output's uri. History UI is out of scope; retry is offered on the result screen of a failed/cancelled job.
- **Organise opens at `/tool/organize/[id]`** after a single-file pick in `/tool/organize` (registry tool `organize`); Files multi-select can jump straight there.

## Review Focus

1. **Huge inputs** (the 50 MB scanned fixture, a 35 MB `content://` share whose provider reports size 0, a 50-file merge of 3 MB files = 150 MB) → refused before bytes reach JS with "larger than 30 MB" / "over 100 MB together", the row is kept, nothing is written, no OOM. Tests: Task 4 (`ToolLimitsTest` stage cap incl. unknown size), Task 7 (`runTool` `tooLarge` from row size and from `ERR_TOO_LARGE`, `totalTooLarge`), Task 13 (device, 50 MB fixture).
2. **Encrypted or corrupt inputs** (protected.pdf, owner-only encrypted, truncated corrupted.pdf, a 0-page PDF) → the job fails naming the offending file ("is password-protected…", "is damaged…"), no output, no row dropped. Tests: Task 3 (`loadPdf` kinds + `inputIndex`), Task 7 (no publish), Task 10 (named message on the result screen).
3. **Name collisions / overwrite** (running the same merge twice; an existing `Documents/PDFToolkit/x merged.pdf` made by another app; two split ranges with the same text) → a new `" (2)"` file every time; the existing file's bytes never change. Tests: Task 4 (`ToolPathsTest.uniqueTarget` with an existing `.part` and target), Task 7 (duplicate range names both published), Task 13 (device: run twice, sha256 of the first output unchanged).
4. **Interrupted tool** (app killed or phone out of space mid-write, user cancels) → no partial or hidden output remains (`.part` / pending MediaStore items removed, workspace deleted), the job reads "The app was closed before this finished", originals byte-identical. Tests: Task 4 (`leftoverParts`, publish failure deletes part), Task 6 (`failInterruptedJobs`), Task 7 (cancel → no publish, workspace cleaned; `ERR_IO` → `io`), Task 13 (device `am force-stop` mid-merge, `ls -a`, sha256).
5. **`content://` inputs** (an "Open with" intent row, a Browse-picked document, a grant revoked after restart, our own FileProvider uri) → read only through the guarded native stage; revoked → "can't read … anymore" with the row kept; own-provider uris refused. Tests: Task 6 (`addPickedDocuments`), Task 7 (`ERR_PERMISSION_DENIED` → `permission`, no `dropMissing`), Task 12 (intent rows selectable), Task 13 (device: merge with an intent row input).
